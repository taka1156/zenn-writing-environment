## はじめに

Next.jsのApp Routerで構築していたブログを、Cloudflareが開発する[vinext](https://github.com/cloudflare/vinext)へ移行してみました。

今回のブログは、Markdownから生成したJSONファイルをビルド時に読み込み、静的HTMLとして出力するSSG構成です。ホスティング先はCloudflare Pagesで、SSRやISRは使用していません。

この記事では、次の2つを紹介します。

- vinextへの移行で、実際に動作確認できた設定
- 移行後に、Vitest・Storybook・commitizenで詰まったところと、その対処

## 何故移行するのか

- TurboPackが結構縛り強いので、今後vite-pluginのエコシステムにのっかれた方が嬉しい。
- Workers Assets配信に移行することも考えてるため。

## Viteの設定

今回の構成では、Cloudflare Workersの実行環境を使わず、Node.js上でSSGを行います。

`vite.config.ts` は以下のようにしました。

```ts:vite.config.ts
import { defineConfig } from 'vite';
import vinext from 'vinext';
import { vanillaExtractPlugin } from '@vanilla-extract/vite-plugin';

export default defineConfig({
  plugins: [
    vanillaExtractPlugin(),
    vinext()
  ]
});
```

ポイントは、`@cloudflare/vite-plugin` を使用していないことです。

Cloudflare Pagesで静的HTMLを配信するだけであれば、ビルド時にCloudflare Workersのランタイムを使う必要はありません。

### vanilla-extractの移行

Next.jsでは `@vanilla-extract/next-plugin` を使用していました。

```js
import { createVanillaExtractPlugin } from '@vanilla-extract/next-plugin';

const withVanillaExtract = createVanillaExtractPlugin();
```

vinextではViteを使用するため、`@vanilla-extract/vite-plugin` に置き換えます。

```bash
yarn add -D @vanilla-extract/vite-plugin
```

既存のCSS Modules相当のスタイル構成を維持しながら、Vite側でvanilla-extractを処理できます。

## Next.jsのStatic Export設定

`next.config.mjs` は以下の構成にします。

```js:next.config.mjs
const nextConfig = {
  output: 'export',
  trailingSlash: true,
  images: {
    unoptimized: true
  }
};

export default nextConfig;
```

主な設定は以下の通りです。

| 設定 | 用途 |
|---|---|
| `output: 'export'` | 静的HTMLとして出力 |
| `trailingSlash: true` | URL末尾にスラッシュを付ける |
| `images.unoptimized: true` | 画像最適化を無効化 |

vanilla-extractの設定はVite側へ移動したため、`withVanillaExtract()` によるラップは不要です。

## SSGでNode.jsのファイルシステムを利用する

今回のブログでは、記事情報をJSONファイルとして保持しています。

記事データを取得する処理は以下のようになっています。

```ts:src/utils/ssg/brite.ts
import { readFile } from 'node:fs/promises';
import { join } from 'node:path';

const CONTENT_PATHS = {
  blog: 'blog/contents',
  portfolio: 'portfolio/contents'
} as const;

const JSON_PATTERN = {
  all: 'all.json',
  category: 'category.json',
  tag: 'tag.json'
} as const;

const getArticle = async <T>(
  contentType: keyof typeof CONTENT_PATHS,
  jsonKey: keyof typeof JSON_PATTERN
): Promise<T | undefined> => {
  try {
    const localPath = join(
      process.cwd(),
      'public',
      CONTENT_PATHS[contentType],
      JSON_PATTERN[jsonKey]
    );

    return JSON.parse(
      await readFile(localPath, 'utf-8')
    ) as T;
  } catch {
    return undefined;
  }
};
```

この処理は、ビルド時に記事データを読み込むことを想定しています。

### Cloudflare Workersランタイムで発生した問題

当初、`vinext init` でCloudflareを選択したところ、開発環境で次のエラーが発生しました。

```text
Error: no such file or directory,
readAll '/bundle/public/blog/contents/all.json'
```

本来は以下のファイルを読み込みたい処理です。

```text
/workspace/public/blog/contents/all.json
```

しかし、Cloudflare Workersランタイムでは、`process.cwd()` が `/bundle` を指していました。

その結果、`node:fs` によるファイル読み込みに失敗していました。

### 解決方法

今回のように、Node.jsで静的ファイルを生成してCloudflare Pagesへデプロイする構成であれば、ViteのCloudflareプラグインを使用しない方法で解決できました。前節の `vite.config.ts` がその構成です。

これにより、開発時のNode.js環境で既存のファイル読み込み処理が動作し、記事一覧が表示されることを確認できました。

公式のサンプルの`vite.config.ts`を見ても`@cloudflare/vite-plugin`が抜かれています。

https://github.com/cloudflare/vinext/tree/main/examples/static-export

重要なのは、**静的HTMLを生成する処理がどのランタイムで実行されるか**です。

Claudeと相談したり、自分で調べてみた結果、大体この様になってるのかなと考えています。

今後、CF/Nitro(Node構成)による環境調査、開発などもしてみて詳細を調べてみます。

## Cloudflare Pagesへのデプロイ

Static Exportで生成されたファイルをCloudflare Pagesへ配置する想定です。

```bash
yarn build
```

出力先は以下です。

```text
dist/client/
```

Cloudflare Pagesでは以下を設定します。

| 設定項目 | 設定値 |
|---|---|
| Framework preset | None |
| Build command | `yarn build` |
| Build output directory | `dist/client` |

この方式では、Cloudflare Workersによるサーバーサイドレンダリングを使用せず、生成済みのHTML・CSS・JavaScriptを配信します。

なお、今回確認できたのは開発サーバーでの記事表示までです。Static Exportによる全ルートのビルドとCloudflare Pagesへのデプロイは別途検証が必要です。

## 移行後に壊れたもの

アプリ本体は動いたものの、周辺ツールで問題が出ました。共通する原因は次の2つです。

- ルートの `vite.config.ts` に `vinext()` を入れたことで、**同じ設定を読むツール（Vitest、Storybook）にも vinext が混ざる**
- vinextの導入で `package.json` に **`"type": "module"`** が入り、CommonJS前提のツールが読み込みに失敗する

vinextのREADMEによると、`vinext init` は `package.json` に `"type": "module"` を追加します。また、`next/*` のimportはすべてVite向けの実装（シム）に解決され、`@vitejs/plugin-react` は自動で登録されます。

### Vitestでの重複と、`mode` による切り分け

Vitestは `vitest.config.ts` がなければ、ルートの `vite.config.ts` を読み込みます。そのため、`vinext()` がテストにも混ざります。

vinextは `@vitejs/plugin-react` を自動で登録します。テストにはReactプラグインが必要ですが、vinextと一緒に手動で足すと、次のエラーになります。

```text
Error: [vinext] Duplicate @vitejs/plugin-react detected.
vinext auto-registers @vitejs/plugin-react by default.
Your config also registers it manually, which duplicates React transforms.
```

設定ファイルを増やしたくなかったので、`vite.config.ts` を関数形式にして、`mode` で切り替えました。Vitestは `mode` を `'test'` として動かすので、テスト時だけvinextの代わりにReactプラグインを使います。

```ts:vite.config.ts
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';
import vinext from 'vinext';
import { vanillaExtractPlugin } from '@vanilla-extract/vite-plugin';
import { resolve } from 'node:path';

export default defineConfig(({ mode }) => ({
  plugins: [
    mode === 'test' ? react() : vinext(), // vinext は React を内包するので二択にする
    vanillaExtractPlugin()
  ],
  resolve: {
    alias: [{ find: '@', replacement: resolve(import.meta.dirname, 'src') }]
  },
  test: {
    environment: 'jsdom'
  }
}));
```

`import.meta.dirname` はNode 20.11以降で使えます。

`process.env.VITEST` で分岐する方法もありますが、Viteが渡す `mode` を使うほうが、環境変数に頼らずに済みます。

### Storybookの「app router to be mounted」エラー

vinextに移行したあと、Storybookで次のエラーが出ました。

```text
Error: invariant expected app router to be mounted
```

`@storybook/nextjs-vite` を使っていて、`preview.ts` には `nextjs.appDirectory: true` も設定済みでした。

原因として有力なのが、StorybookのViteビルダーが、**プロジェクトルートの `vite.config.ts` を自動でマージする**ことです。[公式ドキュメント](https://storybook.js.org/docs/builders/vite#configuration)にも、ビルダーが既存の設定ファイルと一緒にマージする、という説明があります。

つまり、`viteFinal` に何も書いていなくても、ルートの `vite.config.ts` に入った `vinext()` がStorybookに混ざります。vinextは `next/*` を自前のシムに差し替えるので、`@storybook/nextjs-vite` が用意したモックが効かなくなり、本物の `useRouter` がApp Routerのコンテキストを見つけられずにエラーになる、という流れだと考えています。

#### 対処：`viteConfigPath` でルートの設定を読ませない

同じドキュメントの「Override the default configuration」の節に、`viteConfigPath` で読み込む設定ファイルを指定できること、そして**存在しないパスを指定すれば自動で読み込まれない**ことが書かれています。

```ts:.storybook/main.ts
import path from 'node:path';
import { fileURLToPath } from 'node:url';
import type { StorybookConfig } from '@storybook/nextjs-vite';
import { vanillaExtractPlugin } from '@vanilla-extract/vite-plugin';

const __dirname = path.dirname(fileURLToPath(import.meta.url));

const config: StorybookConfig = {
  stories: ['../src/**/*.stories.@(ts|tsx)'],
  addons: ['@storybook/addon-links', '@storybook/addon-docs'],
  framework: {
    name: '@storybook/nextjs-vite',
    options: {
      nextConfigPath: path.resolve(__dirname, '../next.config.mjs')
    }
  },
  core: {
    builder: {
      name: '@storybook/builder-vite',
      options: {
        // 存在しないパスを指定して、ルートの vite.config.ts を読み込ませない
        viteConfigPath: path.resolve(__dirname, 'no-vite-config.ts')
      }
    }
  },
  staticDirs: ['../public'],
  viteFinal: async (config) => {
    const { mergeConfig } = await import('vite');

    // vinext() は入れない。ルートの設定を読まない代わりに、必要なものはここで足す
    return mergeConfig(config, {
      base: './',
      plugins: [vanillaExtractPlugin()],
      resolve: {
        alias: [{ find: '@', replacement: path.resolve(__dirname, '../src') }]
      }
    });
  }
};

export default config;
```

ポイントは3つです。

- ルートの設定を読まなくなるので、`vanillaExtractPlugin()` と `@` のaliasは `viteFinal` に必要です。
- `viteFinal` に `vinext()` を足すと、また重複するので入れません。
- `nextConfigPath` は、移行後の実際のファイル名に合わせます。以前の設定が `../next.config.js` のままだと、`next.config.mjs` を指していないことになります。

個人的には、存在しないパスを読み込ませるというのが、逆に混乱を招くと思い、空の`vite.config.story.ts`を置いて対応しました。

### `"type": "module"` でcz-customizableが動かない

vinextの導入で、`package.json` に `"type": "module"` が入りました。すると、commitizenのアダプターであるcz-customizableが、設定ファイルを読めなくなりました。

```text
Unable to find a configuration file. Please refer to documentation to learn how to set up: ...
Cannot read properties of null (reading 'subjectLimit')
Aborting commit due to empty commit message.
```

使っていたバージョンは、commitizen 4.3.1、cz-customizable 7.2.1です。

`.cz-config.js` は `module.exports = {...}` のCommonJS形式でしたが、`type: module` のもとでは `.js` がESMとして扱われます。cz-customizable側の読み込み処理までは追っていませんが、設定ファイルを `.cjs` にしたら直ったので、これが引き金だったと見ています。

#### 対処：設定ファイルを `.cjs` にして、パスを明示する

```bash
git mv .cz-config.js .cz-config.cjs
```

中身は `module.exports = {...}` のままで構いません。そのうえで、`package.json` の `config` の**中**に、設定ファイルのパスを書きます。

```json:package.json
{
  "config": {
    "commitizen": {
      "path": "node_modules/cz-customizable"
    },
    "cz-customizable": {
      "config": "./.cz-config.cjs"
    }
  }
}
```

## まとめ

Next.jsからvinextへ移行する際、今回の構成で重要だったのは以下の点です。

- Next.jsのApp Routerを維持したままvinextへ移行できた
- `@vanilla-extract/next-plugin` をVite用プラグインに変更した
- `output: 'export'` を維持してSSG構成を採用した
- Cloudflare Pagesで静的配信するため、Workersランタイムを使用しない構成にした
- Node.jsの `node:fs` を使用する記事読み込み処理を維持できた

また、移行後の周辺ツールでは、次の点に注意が必要でした。

- ルートの `vite.config.ts` は、VitestやStorybookにも読み込まれる。vinextは `next/*` のシムとReactプラグインを持ち込むので、テストやStorybookでは外す必要がある
- Vitestは `mode` で切り替え、Storybookは `viteConfigPath` でルートの設定を読ませない
- vinextが入れる `"type": "module"` は、CommonJS前提のツールに影響する。設定ファイルは `.cjs` にする

vinextへの移行では、Next.jsのAPI互換性だけでなく、**開発時・ビルド時・テスト時にどのランタイムと設定を使用するか**が重要だと分かりました。

特にCloudflare PagesでSSGのみを利用する場合、Cloudflare Workersの実行環境を組み込む必要があるとは限りません。既存のNode.jsによるSSG処理を維持したい場合は、シンプルなVite + vinext構成も選択肢になります。
